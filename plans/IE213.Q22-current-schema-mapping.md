# IE213.Q22 - Current PostgreSQL Schema to MongoDB Mapping

## Purpose

This document maps the latest SQL schema supplied for branch `IE213.Q22` into MongoDB collections. The local MongoDB target is `intelligentroutex` and is started by `docker-compose.mongodb.yml`.


## Design Rules

- SQL UUIDs are represented as string IDs in MongoDB.
- Primary keys map to `_id` where practical; legacy integer IDs such as `order_files.id` can use integer `_id`.
- Foreign keys become application-level references, e.g. `user_id`, `order_id`, `master_order_id`.
- `jsonb` fields become native MongoDB objects or arrays.
- SQL enum/check constraints become JSON Schema enum validators.
- Validators use `validationAction: 'warn'` during migration so legacy/imported records do not block setup.
- Unique SQL constraints become MongoDB unique indexes.
- TTL indexes are used for expiring tokens/sessions.

## Important Model Notes

### `profiles`

This schema uses `profiles` as the main user collection, not `users`. Most user references point to `profiles._id`.

### Orders

The schema has multiple order concepts:

- `master_orders`: parent checkout/payment summary.
- `orders`: legacy/direct order records with `ready_made`, `custom`, and `printing` types.
- `order_parent` and `order_child`: newer parent/child order-code structure.
- `custom_orders` and `print_orders`: specialized order collections tied to `master_orders`.

Do not merge these collections until application code has one canonical order model.

### Payments

There are two payment collections:

- `payment`: parent/child/direct_child QR payment records.
- `payments`: legacy order payment records with deposit/full/remaining payment type.

Keep both during migration because routes may reference both names.

### Backups

The `_backup_*` collections are included because they exist in the supplied SQL schema. They should not be used by new application code unless a recovery/import task needs them.
